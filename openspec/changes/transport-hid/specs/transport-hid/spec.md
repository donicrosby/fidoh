# Delta: transport-hid

## ADDED Requirements

### Requirement: CTAPHID framing over 64-byte HID reports

The HID transport SHALL frame every CTAP message in fixed 64-byte HID
reports per CTAP2.1 §11.2.4, as one of two packet types. An
initialization packet SHALL carry: a 4-byte CID (channel identifier,
big-endian), a 1-byte CMD with bit 7 always set (§11.2.4: "The command
byte has always the highest bit set to distinguish it from a
continuation packet"), a 2-byte BCNT payload length (high byte at
offset 5, low byte at offset 6, big-endian), and payload data in the
remaining 57 bytes. A continuation packet SHALL carry: the 4-byte CID,
a 1-byte SEQ (0x00..0x7F, bit 7 always cleared), and payload data in
the remaining 59 bytes. Packets SHALL always be sent at full 64-byte
size; unused bytes SHOULD be set to zero (§11.2.4). A message with
payload ≤ 57 bytes fits one packet; larger messages are split into
continuation packets. The maximum message payload length SHALL be
7609 bytes (§11.2.4: 64 − 7 + 128 × (64 − 5) = 7609). All multi-byte
integers on the wire are big-endian (§8: "All values are big endian
encoded"). The library SHALL reject, with a typed error, an outgoing
CTAP message whose payload exceeds 7609 bytes before transmitting any
packet.

| Offset | Init packet | Continuation packet |
|---|---|---|
| 0–3 | CID (4 bytes) | CID (4 bytes) |
| 4 | CMD (bit 7 set) | SEQ (0x00..0x7F) |
| 5–6 | BCNT (2 bytes, big-endian) | — |
| 7–63 | payload (57 bytes) | payload (59 bytes) |

#### Scenario: Single-packet message

- **WHEN** the transport sends a CTAP message whose total payload
  (command byte plus encoded data) is ≤ 57 bytes
- **THEN** exactly one 64-byte initialization packet is written, the
  CMD byte has bit 7 set, BCNT equals the payload length, and unused
  trailing bytes are zero; the write is a single bounded packet send
  within the remaining ceremony budget (async-core D4), returning the
  typed `Timeout` naming the transmit phase on expiry

#### Scenario: Multi-packet message uses ascending sequence numbers

- **WHEN** the transport sends a CTAP message whose payload exceeds
  57 bytes
- **THEN** it writes one initialization packet carrying the first 57
  payload bytes followed by continuation packets of 59 payload bytes
  each, SEQ starting at 0x00 and incrementing by one per packet
  (CTAP2.1 §11.2.4), with the final packet zero-padded to 64 bytes;
  the complete transmit is bounded by the remaining ceremony budget
  (async-core D4), returning the typed `Timeout` naming the transmit
  phase on expiry

#### Scenario: Oversized message rejected before transmission

- **WHEN** the caller issues a CTAP command whose payload would exceed
  7609 bytes (CTAP2.1 §11.2.4 maximum message length)
- **THEN** the transport fails with a typed message-length error and
  writes no packet to the device; the wait this implies is bounded by
  the remaining ceremony budget (async-core D4) and on expiry returns
  the typed `Timeout` naming the framing phase

#### Scenario: Transaction concurrency (CI: transport-soft parity)

- **WHEN** a getAssertion command is exchanged over the HID transport
  while the soft transport runs the same exchange in CI (keepalive
  knob sequence, transport-soft)
- **THEN** the HID path observes the same transaction semantics as
  CTAP2.1 §11.2.5.1: the request is atomic from first init packet to
  the last packet of the response, and the transport does not interleave
  another request on the same channel mid-transaction

### Requirement: Channel allocation via CTAPHID_INIT on the broadcast CID

The HID transport SHALL allocate every channel by sending CTAPHID_INIT
(command 0x06) on the broadcast CID 0xFFFFFFFF with an 8-byte nonce
generated by the host, per CTAP2.1 §11.2.9.1.3. The INIT response
(BCNT 17) SHALL carry, in order: the 8-byte nonce (echoed), a 4-byte
channel ID, the CTAPHID protocol version identifier (2 for this
protocol version), a 3-byte vendor-defined device version
(major/minor/build), and a 1-byte capabilities flags field. The
transport SHALL match the echoed nonce against the nonce sent and
SHALL treat a nonce mismatch as a typed framing error, not as a
channel allocation (§11.2.9.1.3: the nonce "is used to match the
response"). A host SHALL accept a response longer than 17 bytes for
forward compatibility (§11.2.9.1.3 note). Channel ID 0 is reserved
and 0xFFFFFFFF is reserved for broadcast (§11.2.3); an INIT response
yielding either value SHALL be a typed error. Capabilities bits
(§11.2.9.1.3): CAPABILITY_WINK 0x01 (implements CTAPHID_WINK),
CAPABILITY_CBOR 0x04 (implements CTAPHID_CBOR), CAPABILITY_NMSG 0x08
(DOES NOT implement CTAPHID_MSG); unused bits are reserved and MUST be
zero from vendors. Channel allocation SHALL be bounded by the
remaining ceremony budget (async-core D4); on expiry it SHALL return
the typed `Timeout` naming the channel-allocation phase.

#### Scenario: Allocate a channel with nonce match

- **WHEN** the transport sends CTAPHID_INIT with an 8-byte nonce on
  CID 0xFFFFFFFF and the device replies with the same nonce, a fresh
  4-byte channel ID, protocol version 2, and a capabilities byte
- **THEN** the transport stores the channel ID for subsequent
  transactions on this connection and exposes the capabilities byte to
  the rest of the library; the allocation exchange is bounded by the
  remaining ceremony budget (async-core D4), returning the typed
  `Timeout` naming the channel-allocation phase on expiry

#### Scenario: Nonce mismatch fails the allocation

- **WHEN** the INIT response carries a nonce different from the one
  sent (e.g. two hosts allocate concurrently on one device)
- **THEN** the allocation fails with a typed nonce-mismatch error and
  the received channel ID is not used; the transport MAY retry the
  INIT within the remaining ceremony budget, and on budget expiry
  returns the typed `Timeout` naming the channel-allocation phase

#### Scenario: INIT on an allocated channel resynchronizes

- **WHEN** the transport sends CTAPHID_INIT on an already allocated
  channel ID (not the broadcast CID)
- **THEN** the current transaction, buffers, and state on that channel
  are discarded by the device and the channel is ready for a new
  transaction (CTAP2.1 §11.2.9.1.3 / §11.2.5.3 abort-and-
  resynchronization), and this resynchronization hop is bounded by the
  remaining ceremony budget with typed `Timeout` on expiry

### Requirement: Capability-gated commands and the capabilities byte

The HID transport SHALL gate CTAPHID_WINK (0x08) on the
CAPABILITY_WINK (0x01) bit of the INIT response capabilities byte and
SHALL gate use of CTAPHID_CBOR (0x10) on CAPABILITY_CBOR (0x04), per
the capabilities table in CTAP2.1 §11.2.9.1.3. When a gated command is
requested but its capability bit is 0, the transport SHALL fail with a
typed unsupported-operation error without writing the command to the
device. The CAPABILITY_NMSG (0x08) bit SHALL be recorded and surfaced
as device metadata (the device does not implement CTAPHID_MSG);
v1 behavior does not depend on CTAPHID_MSG, so NMSG devices remain
fully usable for CTAP2 (CBOR) ceremonies. A wink request SHALL be
bounded by the remaining ceremony budget (async-core D4); on expiry it
SHALL return the typed `Timeout` naming the wink phase.

#### Scenario: Wink sent only when the device advertises it

- **WHEN** the caller requests wink on a device whose capabilities
  byte has CAPABILITY_WINK set
- **THEN** the transport sends CTAPHID_WINK (0x08, BCNT 0) on the
  allocated channel and completes when the device echoes the command
  with BCNT 0 (CTAP2.1 §11.2.9.2.1), within the remaining ceremony
  budget, returning the typed `Timeout` naming the wink phase on expiry

#### Scenario: Wink refused when not advertised

- **WHEN** the caller requests wink on a device whose capabilities
  byte has CAPABILITY_WINK clear
- **THEN** the transport returns a typed unsupported-operation error
  immediately and no wink command is written to the device

### Requirement: CTAPHID_CANCEL on caller cancellation

When the caller cancels (drops the ceremony/device future or invokes
an explicit cancel) while a CTAPHID_CBOR request is outstanding on the
channel, the transport SHALL send CTAPHID_CANCEL (0x11, BCNT 0) on the
same channel, per CTAP2.1 §11.2.5.3 ("If an application wishes to
abort a command after the request has been fully sent … the
application MAY do this by sending a CTAPHID_CANCEL command") and
§11.2.9.1.5. The transport SHALL NOT wait for or expect any response
to CTAPHID_CANCEL itself (§11.2.9.1.5: "the authenticator MUST NOT
reply to the CTAPHID_CANCEL message itself"). If the cancelled
request's response arrives as CTAP1_ERR/0x2D
CTAP2_ERR_KEEPALIVE_CANCEL, the transport SHALL surface that status to
the ceremony layer (which maps it to `Error::UserCancelled` per the
ceremony change's typed status-code handling). A CTAPHID_CANCEL sent
while no request is outstanding SHALL be avoided by the transport (the
authenticator ignores it per §11.2.9.1.5, and sending it is pointless
traffic). Sending CTAPHID_CANCEL SHALL be bounded by the remaining
ceremony budget (async-core D4); on expiry the send SHALL return the
typed `Timeout` naming the cancel phase, and if the budget has already
expired the cancel MAY be skipped (best-effort release semantics per
async-core D4/OQ-3).

#### Scenario: Caller cancels during user-presence wait

- **WHEN** the caller drops the ceremony future or issues an explicit
  cancel while the device is emitting keepalives for an outstanding
  getAssertion (user-presence wait in flight)
- **THEN** the transport writes CTAPHID_CANCEL (0x11, BCNT 0) on the
  same channel (CTAP2.1 §11.2.9.1.5), does not wait for a reply to the
  cancel itself, and the subsequently received
  CTAP2_ERR_KEEPALIVE_CANCEL response is surfaced as the request's
  response, mapped to `Error::UserCancelled` by the ceremony layer;
  the cancel send is bounded by the remaining ceremony budget and is
  best-effort only if that budget is already exhausted (async-core
  OQ-3)

#### Scenario: Cancel send is bounded

- **WHEN** the caller cancels while a keepalive loop is in flight and
  the remaining ceremony budget is already exhausted
- **THEN** the transport attempts the CTAPHID_CANCEL send on a
  best-effort basis bounded by no new budget; if the send cannot
  complete, the error is swallowed per async-core's mandatory-best-
  effort channel-release decision, and the device remains usable for a
  subsequent ceremony (worst case after one INIT re-handshake,
  CTAP2.1 §11.2.5.3)

### Requirement: CTAPHID_ERROR mapping to typed transport errors

The HID transport SHALL decode CTAPHID_ERROR (0x3F, BCNT 1) responses
into typed transport errors carrying the one-byte error code, per the
error-code table in CTAP2.1 §11.2.9.1.6: ERR_INVALID_CMD 0x01 (the
command in the request is invalid), ERR_INVALID_PAR 0x02 (the
parameter(s) in the request are invalid), ERR_INVALID_LEN 0x03 (the
length field BCNT is invalid for the request), ERR_INVALID_SEQ 0x04
(the sequence does not match the expected value), ERR_MSG_TIMEOUT
0x05 (the message has timed out), ERR_CHANNEL_BUSY 0x06 (the device is
busy for the requesting channel; the client SHOULD retry the request
after a short delay and MAY abort the transaction if the command is no
longer relevant), ERR_LOCK_REQUIRED 0x0A (command requires channel
lock), ERR_INVALID_CHANNEL 0x0B (CID is not valid), ERR_OTHER 0x7F
(unspecified error). The transport SHALL surface each code as a
distinct typed variant (unknown codes as a typed catch-all, never an
untyped error, matching core-model's total status-code posture). On
ERR_CHANNEL_BUSY the transport SHALL retry the request after a short
`Sleep`-driven delay (async-core Sleep trait) while budget remains;
each retry slice is bounded by the remaining ceremony budget and
exhaustion returns the typed `Timeout` naming the busy-retry phase.

#### Scenario: Busy error triggers bounded retry

- **WHEN** a CTAPHID_CBOR request receives CTAPHID_ERROR with
  ERR_CHANNEL_BUSY (0x06) and ceremony budget remains
- **THEN** the transport re-issues the request after a `Sleep`-driven
  delay (CTAP2.1 §11.2.9.1.6 client-SHOULD-retry), with every retry
  bounded by the remaining ceremony budget; on budget expiry the
  transport returns the typed `Timeout` naming the busy-retry phase

#### Scenario: Error codes map to typed variants

- **WHEN** the device responds with CTAPHID_ERROR carrying any code
  from 0x01, 0x02, 0x03, 0x04, 0x05, 0x0A, 0x0B, 0x7F (or an unknown
  code)
- **THEN** the transport surfaces exactly one typed error naming that
  code (or the typed unknown catch-all), with no retry except the
  ERR_CHANNEL_BUSY retry path

### Requirement: CTAPHID_KEEPALIVE surfaced as progress signals with budget-bounded waits

The HID transport SHALL decode CTAPHID_KEEPALIVE (0x3B, BCNT 1,
status byte per CTAP2.1 §11.2.9.1.7) messages arriving between a
request and its response: STATUS_PROCESSING (0x01, the authenticator
is still processing) and STATUS_UPNEEDED (0x02, the authenticator is
waiting for user presence). A keepalive does not constitute a response
and does not end the ongoing transaction (§11.2.9.1.7). Every
keepalive with status STATUS_UPNEEDED SHALL be surfaced to the caller
as a progress signal (async-core Device requirement; ceremony change
keepalive-progress requirement) — never swallowed, never returned as
an error. Every keepalive wait SHALL be bounded by the remaining
ceremony budget (async-core D4 single-budget model), re-sliced at most
`DEFAULT_WAIT_SLICE` (30 s, crate-public, caller-overridable per the
async-core resolved decision) per read so a dropped future
re-detects cancellation; on budget exhaustion the wait SHALL terminate
with the typed `Timeout` naming the user-presence (or processing)
phase. An unbounded keepalive wait is a spec violation (async-core
Sleep requirement: "An unbounded wait is a spec violation"). Upon
receiving a keepalive the transport SHALL NOT resend the request
(the §11.4.9 BLE client rule, carried over to HID by analogy: §11.2.9.1.7 defines keepalives but states no resend rule
transaction model).

#### Scenario: Up-needed keepalives surface as progress until response

- **WHEN** the device emits three CTAPHID_KEEPALIVE messages with
  STATUS_UPNEEDED (0x02) and then the CTAPHID_CBOR response
- **THEN** the caller observes three keepalive progress signals with
  status up-needed in order, then the response; no signal is delivered
  as an error, and the entire wait is bounded by the remaining
  ceremony budget

#### Scenario: Budget exhaustion during up-needed terminates typed

- **WHEN** the device keeps emitting STATUS_UPNEEDED (0x02)
  keepalives and the ceremony budget expires before user presence
- **THEN** the keepalive wait terminates at the budget boundary with
  the typed `Timeout` naming the user-presence phase; the transport
  sends CTAPHID_CANCEL on the channel (per the CTAPHID_CANCEL-on-
  caller-cancellation requirement), and the device remains usable for
  a subsequent ceremony
- **AND** the wait is bounded by the remaining ceremony budget only —
  no other timer extends it, and no code path may wait unboundedly
  (async-core Sleep requirement)

#### Scenario: Per-wait slice keeps drop-cancellation responsive

- **WHEN** a keepalive wait lasts longer than the crate-public
  `DEFAULT_WAIT_SLICE` (30 s default, caller-overridable) and the
  caller dropped the ceremony future mid-wait
- **THEN** the wait re-slices at the slice boundary (async-core
  blocking-syscall policy), the detached blocking read exits within
  at most one slice — at most 30 s by default, the slice bounding
  cancellation latency only and never extending the total wait, which
  remains bounded by the remaining ceremony budget — and a subsequent
  `connect` on the same authenticator succeeds

#### Scenario: Processing keepalives do not reset the budget

- **WHEN** the device emits STATUS_PROCESSING (0x01) keepalives while
  computing a response
- **THEN** the transport surfaces them as progress with status
  processing, continues waiting within the same single budget (no
  budget reset, async-core D4), and returns the response when it
  arrives before the budget expires

### Requirement: Message reassembly and packet ordering rules

The HID transport SHALL reassemble request and response messages per
CTAP2.1 §11.2.4/§11.2.5.4: continuation packets carry SEQ starting at
0x00 and incrementing by one per packet; the transport SHALL expect
exactly that sequence on its channel. A continuation packet with an
unexpected SEQ SHALL be treated as the typed ERR_INVALID_SEQ framing
error (CTAP2.1 §11.2.9.1.6: "The sequence does not match expected
value" per §11.2.9.1.6's error table). Packets arriving on a CID other
than the transport's allocated channel SHALL be ignored (they belong
to other clients sharing the device; §11.2.3 concurrency model), with
one exception: a CTAPHID_ERROR ERR_CHANNEL_BUSY addressed to the
transport's channel while the transport awaits device-idle after its
own transaction is aborted. A spurious continuation packet arriving
without a prior initialization packet SHALL be ignored, matching the
device-side rule (§11.2.5.4: "Spurious continuation packets appearing
without a prior initialization packet will be ignored"). The
interval between packets of one message SHALL be bounded: if the next
expected packet has not arrived within the remaining ceremony budget
(CTAP2.1 §11.2.5.2 transaction timeout fixes no specific duration —
see design OQ-1), the reassembly SHALL abort with the typed `Timeout`
naming the reassembly phase and the channel SHALL be resynchronized
via INIT-on-allocated-CID (§11.2.5.3) before reuse.

#### Scenario: Correct sequence reassembles

- **WHEN** a response arrives as one initialization packet followed by
  two continuation packets with SEQ 0x00 and 0x01 on the allocated CID
- **THEN** the transport reassembles the 57 + 59 + 59 payload bytes,
  truncates to the BCNT length, and delivers the message; the whole
  reassembly wait is bounded by the remaining ceremony budget
  (async-core D4), returning the typed `Timeout` naming the reassembly
  phase on expiry

#### Scenario: Wrong sequence number aborts with typed error

- **WHEN** a continuation packet arrives with SEQ not equal to the
  expected value (e.g. 0x02 where 0x00 is expected)
- **THEN** reassembly aborts with the typed invalid-sequence framing
  error (CTAP2.1 §11.2.9.1.6 ERR_INVALID_SEQ), and the transport
  resynchronizes the channel via INIT-on-allocated-CID
  (CTAP2.1 §11.2.5.3) bounded by the remaining ceremony budget
  (typed `Timeout` naming the resync phase on expiry)

#### Scenario: Foreign-CID traffic is ignored

- **WHEN** a packet arrives on a CID other than the allocated channel
  while the transport waits for its response
- **THEN** the packet is discarded without disturbing the pending
  transaction (CTAP2.1 §11.2.3 channels isolate concurrent clients),
  and the pending wait remains bounded by the remaining ceremony
  budget

#### Scenario: Spurious continuation packet ignored

- **WHEN** a continuation packet arrives on the allocated CID while no
  message reassembly is in progress
- **THEN** the transport ignores it (device-side mirror of CTAP2.1
  §11.2.5.4) and continues waiting for the actual response within the
  remaining ceremony budget

#### Scenario: Inter-packet timeout aborts reassembly

- **WHEN** the next expected packet of a message in progress does not
  arrive before the remaining ceremony budget is exhausted
  (CTAP2.1 §11.2.5.2 fixes no numeric transaction-timeout value)
- **THEN** reassembly aborts with the typed `Timeout` naming the
  reassembly phase and the channel is resynchronized via
  INIT-on-allocated-CID before the next transaction

### Requirement: Channel lock (CTAPHID_LOCK) is not used in v1

The HID transport SHALL NOT send CTAPHID_LOCK (0x04) in v1 and SHALL
NOT require a channel lock for any command it issues (CTAP2.1 §11.2.6:
channel locking is optional and "has not to be considered by general
CTAP HID applications"). Because the transport never sends a locked
command, an ERR_LOCK_REQUIRED (0x0A) response is not expected; if one
arrives anyway it SHALL surface as the typed lock-required error
without retry. The decision and its rationale are recorded in this
change's design.md (Alternatives).

#### Scenario: No lock command on the wire

- **WHEN** any ceremony, channel allocation, wink, or cancel operation
  runs over the HID transport
- **THEN** no CTAPHID_LOCK (0x04) packet is written to the device, and
  all arbitration relies on channel allocation plus the device's own
  transaction atomicity (CTAP2.1 §11.2.5.1); this is a property
  checked on the write path, with any lock-related wait bounded by the
  remaining ceremony budget (async-core D4) like every other hop

#### Scenario: Unexpected lock-required surfaces typed

- **WHEN** a device responds with CTAPHID_ERROR ERR_LOCK_REQUIRED
  (0x0A) despite the transport never locking
- **THEN** the transport surfaces the typed lock-required error with
  no retry, within the remaining ceremony budget

### Requirement: Linux hidraw enumeration filtered by FIDO usage page and usage

On Linux the HID transport's `Transport::enumerate` SHALL discover
candidate devices by scanning hidraw device nodes (`/dev/hidraw*`)
via the kernel's hidraw class/sysfs interface (kernel hidraw doc:
udev creates hidraw nodes directly under /dev and "applications should
use libudev to locate hidraw devices attached to the system"). For each
candidate the transport SHALL read the device's HID report descriptor
(sysfs `report_descriptor` attribute exposed for HID devices by the
kernel) and include the device as a FIDO candidate only when the
descriptor declares usage page 0xF1D0 (FIDO alliance usage page) with
usage 0x01 (CTAPHID), per CTAP2.1 §11.2.8.2: "A unique Usage Page is
defined (0xF1D0) for the FIDO alliance and under this realm, a CTAPHID
Usage is defined as well (0x01). During CTAPHID device discovery, all
HID devices present in the system are examined and devices that match
this usage pages and usage are then considered to be CTAPHID devices."
Enumeration SHALL NOT filter by USB vendor ID or product ID — any
vendor's device matching the usage filter is a candidate (CTAP2.1
§11.2.8.2 names no VID/PID restriction). Enumeration SHALL be bounded
by the remaining ceremony budget (async-core D4); on expiry it SHALL
return the typed `Timeout` naming the enumeration phase.

#### Scenario: FIDO usage match is enumerated regardless of vendor

- **WHEN** two hidraw nodes exist, one whose report descriptor carries
  usage page 0xF1D0 / usage 0x01 (any VID/PID) and one keyboard
  (usage page 0x01)
- **THEN** enumeration yields exactly the FIDO-usage node as a
  candidate, with no VID/PID-based exclusion applied; enumeration is
  bounded by the remaining ceremony budget (async-core D4), returning
  the typed `Timeout` naming the enumeration phase on expiry

#### Scenario: Enumeration is budget-bounded

- **WHEN** the sysfs scan is slow or the descriptor read stalls beyond
  the remaining ceremony budget
- **THEN** enumeration returns the typed `Timeout` naming the
  enumeration phase; a candidate found before expiry is not delivered
  after expiry (the whole phase is bounded by the single budget,
  async-core D4)

#### Scenario: Unreadable report descriptor degrades, not fails

- **WHEN** one hidraw node's `report_descriptor` cannot be read
  (permission or race with unplug) during enumeration
- **THEN** that node is skipped and recorded as a diagnostic, the scan
  continues, and remaining candidates are still returned (ceremony
  change: per-transport discovery errors are collected, never abort
  discovery); the scan as a whole stays bounded by the remaining
  ceremony budget, returning the typed `Timeout` naming the
  enumeration phase on expiry
