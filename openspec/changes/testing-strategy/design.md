# Design: testing-strategy

**Phase: D** (cross-cutting verification strategy, per the phased authoring
plan; spec-authoring only — no code in this change).

The phase map lives in the cryptile workspace plan
(`.hermes/plans/2026-09-22-cleanroom-ctap2-library-specs.md`) until a local
one is authored for this repo.

## Architecture

Verification is layered so that each layer depends only on layers beneath it
and each layer's environment requirements are strictly weaker than the layer
above:

```
        ┌─────────────────────────────────────┐
   T3   │ Hardware tests (manual, opt-in)     │  physical keys, human at the desk
        ├─────────────────────────────────────┤
   T2   │ Soft-token integration tests        │  default-on, CI, no hardware/root/udev
        ├─────────────────────────────────────┤
   T1   │ Unit tests (pure CBOR/model logic)  │  default-on, everywhere `cargo test` runs
        └─────────────────────────────────────┘
```

- **T1 unit tests** live next to core-model code. They need no async runtime,
  no I/O, no fixtures beyond byte strings. They pin canonical-CBOR encode and
  strict-decode behavior (core-model requirements 1–3), the wire structures,
  and the CTAP2.1 §8.2 status table.
- **T2 soft-token integration tests** run the full client ceremony stack
  (discovery → selection → getInfo probe → getAssertion → drain) against
  transport-soft. Because the soft token performs zero OS I/O and shares the
  hardware code path by trait parity (transport-soft requirement: trait
  parity), T2 exercises the real client code end to end. T2 is the **only**
  tier that must pass in default CI, and it must pass on hosted runners:
  no USB devices, no root, no udev rules, no pcscd.
- **T3 hardware tests** run the same ceremony against physical
  authenticators. They are never compiled or run by default; a cargo feature
  (e.g. `hardware-tests`) or env gate (e.g. `FIDOH_HARDWARE_TESTS=1`) —
  decided at implementation — arms them. `docs/testing.md` is the manual
  runbook.

## Blocking waits and timeout bounds

This change authors documents and test *requirements*, not tests; the only
waits it names are bounds on the tests themselves:

- Every T2 scenario that waits (keepalive sequences, require-explicit-poke,
  delay-beyond-deadline) is bounded by the caller-supplied ceremony deadline
  exactly as the ceremony spec requires; the delay-beyond-deadline knob's own
  hard cap of deadline + 60 s (transport-soft design) bounds the token side.
  No T2 test may sleep longer than that cap.
- T3 hardware UP-required waits are bounded by the ceremony deadline the
  runbook prescribes (30 s default, matching async-core's tunable wait-slice
  discussion); a test that does not observe the expected typed outcome within
  the deadline fails, it does not hang.

## Decision: soft-token tier is the CI contract

Every typed error variant in the ceremony taxonomy (ten variants per the
ceremony spec) must be reachable from T2 alone. This is achievable because
transport-soft's knobs cover: arbitrary status injection (a), keepalive
sequences (b), delay-beyond-deadline (c), wrong-credential-id (d), plus
UP/UV modes and multi-instance scenarios (two tokens → `AmbiguousDevice`;
zero transports → `NoDevice`). The spec enumerates the mandatory scenario
list so an implementation cannot claim CI-green while skipping failure paths.

## Decision: conformance vector provenance

Two vector sources, two labels, per the config.yaml docs rule (worked
examples labeled constructed-vs-captured) and the cleanroom rules:

1. **Spec-derived**: byte strings transcribed from the CTAP2 spec's own
   examples (CTAP2.1 §6 command/response examples where present). Labeled
   *spec-derived*. These are ground truth for canonical CBOR.
2. **Constructed**: generated by transport-soft under a deterministic seeded
   RNG (transport-soft requirement: deterministic fixtures), committed, and
   regenerated in CI to assert byte-identical reproduction. Labeled
   *constructed*. Never captured from a third-party authenticator — captured
   blobs are a cleanroom provenance risk and are excluded.

## Decision: fuzzing scope

The CBOR decoder is the single mandatory fuzz target. Rationale: it is the
only component that parses fully attacker-controlled bytes arriving from a
USB/NFC device the host does not trust; a panic or unbounded allocation there
is reachable from hardware. cargo-fuzz (libFuzzer) or an equivalent
coverage-guided fuzzer is required at the implementation phase; the spec pins
the requirement, not the tool version. CTAPHID/APDU framing layers are
candidate future targets but are not mandated in v1 — their inputs are
length-prefixed and structurally simpler than CBOR.

## Alternatives considered

- **Hardware-in-the-loop CI as the primary gate.** Rejected: hosted runners
  have no USB passthrough; self-hosted runners with attached keys are fragile
  (udev drift, key wear, shared-state flakiness) and cannot gate PRs from
  forks. Hardware tests stay manual/opt-in; the soft token's trait parity
  makes T2 a faithful substitute for logic verification.
- **Mock the Device trait instead of a full soft authenticator.** Rejected
  (already decided in transport-soft design): a mock returns canned bytes and
  cannot produce real signatures over arbitrary clientDataHash values, so
  signature-adjacent paths go untested.
- **Record/replay captured authenticator traffic for fixtures.** Rejected:
  cleanroom rules forbid treating captured third-party behavior as protocol
  truth, and replayed blobs cannot respond to varying inputs.
- **Nightly-only fuzzing with no CI signal.** Rejected for the decoder smoke
  target: a short bounded fuzz run in CI (time-boxed, e.g. a few minutes)
  catches regressions at PR time; long campaign fuzzing runs separately. The
  spec requires the CI smoke run and leaves campaign duration to
  implementation.
- **MSRV tested only via `cargo check`.** Rejected: async-core OQ-1 resolved
  that CI MUST compile *and test* on exactly 1.75 plus stable; `check` alone
  would miss test-only code that violates MSRV.

## Open questions

1. Gate mechanism for T3: cargo feature `hardware-tests` vs env var
   `FIDOH_HARDWARE_TESTS=1`. A feature changes the compile graph; an env var
   risks silently skipping when unset. Recommendation: cargo feature,
   confirmed at implementation.
2. CI fuzz smoke-run duration. Too short finds nothing; too long slows every
   PR. Recommendation: 60–120 s bounded run, corpus committed.
3. Whether the T2 scenario matrix is enforced structurally (one test function
   per named scenario, asserted by a compile-time list) or by review.
   Recommendation: test names match scenario IDs in the spec; enforcement by
   review for v1.
